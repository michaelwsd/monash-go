Part one

How an authenticated request wires together

A token arrives as a string in a header and reaches your route body as a typed ClerkClaims object. Nothing in the codebase calls the route to make that happen. This traces every hand-off in between, and names the file and line where each one lives.

Orientation

Four layers, one direction

Every file below belongs to exactly one layer, and a layer may only import from the layers beneath it. That single rule is what the whole chain is arranged to protect: HTTP concepts stop at the top, and the bottom layer never learns that a web request exists.

api/ Parse, validate, call a service, shape a response. Where Depends is allowed to appear.
services/ Business logic. Raises domain errors, never HTTPException.
repositories/ Every Supabase call. Returns domain models, never raw dicts.
core/ Pure functions and config. Zero I/O, and no idea what a request is.
imports flow downward only ↓
Why the token logic is split across two layers. core/security.py takes a token string and returns claims. It never touches a Request, which is what lets tests/unit/test_security.py hand it a self-signed token with no HTTP anywhere. api/deps.py is the thin adapter that knows how to pull that string out of a real request.
The happy path

One request, seven hand-offs

Steps 2 to 6 are all resolved by FastAPI before your route body runs. Step 7 is the first ordinary Python call you wrote yourself.

  1. 1
    Clerk signs the token external

    The user signs in with Google. Clerk mints a JWT and signs it with its private key, which never leaves Clerk. The frontend attaches it to every call.

    Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyXzJhYmMxMjMi...
    hands on → an HTTP request
  2. 2
    bearer_scheme app/api/deps.py:35 api/

    An HTTPBearer instance built once at import time. It is not a value that comes from the request — it is the callable that reads one.

    bearer_scheme = HTTPBearer(auto_error=False)

    It is a dependency like any other, not a special case: HTTPBearer.__call__ declares a Request parameter, so FastAPI injects the request into it the same way it injects claims into your route. It then splits the header on the space, checks the scheme reads Bearer, and wraps the rest.

    in
    Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJ1c2VyXzJhYmMxMjMifQ...
    out
    HTTPAuthorizationCredentials
    .scheme"Bearer"the part it validated
    .credentials"eyJhbGciOiJSUzI1NiJ9..."the token, what step 4 verifies
    or
    None — header absent, or present but not Bearer <something>

    That None is the whole point of auto_error=False. The default makes HTTPBearer raise its own HTTPException, producing a response your error handler never sees. Switched off, it returns None and the decision of what a missing header means stays yours — which is what step 3 acts on.

    It does not run on every request. Only routes that depend on it, directly or through CurrentClaims and CurrentUser, ever call it. /health takes only SettingsDep, so no header is read and no token is verified there at all.
    hands on → HTTPAuthorizationCredentials | None
  3. 3
    get_current_claims app/api/deps.py:39 api/

    Catches the None that step 2 can now produce, then delegates the actual cryptography downward. Note its own parameter is annotated the same way — that is how the chain links.

    def get_current_claims(
    credentials: Annotated[HTTPAuthorizationCredentials | None, Depends(bearer_scheme)],
) -> ClerkClaims:
    if credentials is None:
        raise InvalidCredentialsError("missing or malformed authorization header")
    return verify_clerk_token(credentials.credentials)
    hands on → ClerkClaims
  4. 4
    verify_clerk_token app/core/security.py:35 core/

    The real gate. Four independent checks, any one of which fails the whole request. Because RS256 is asymmetric, your server holds only the public key: it can verify any token but forge none, and it never calls Clerk over the network to do it.

    CheckComes fromCatches
    signatureclerk_pem_public_keyforged or tampered payload
    expthe tokena stale token replayed later
    issuerclerk_issuera valid token from someone else's Clerk app
    require=[…]the tokena Clerk template that was never configured
    hands on → dict
  5. 5
    ClerkClaims app/core/security.py:50 core/

    A second try block, for a reason worth stating plainly: require only proves a claim exists. jwt.decode returns a plain dict, so claims["email"] could be the number 42 and still pass step 4. This is where the payload becomes typed.

    Both failures raise the same InvalidCredentialsError with the same message. That is intentional — an error that distinguishes "expired" from "bad signature" tells an attacker which half to keep working on.

    hands on → ClerkClaims(clerk_id, email, full_name)
  6. 6
    sync_user app/api/routes/users.py:11 api/

    Only now does the body run. Both parameters were filled in by FastAPI, decided by the annotation and never by the parameter name.

    def sync_user(claims: CurrentClaims, db: SupabaseDep) -> User:
    hands on → a real ClerkClaims and a real Client
  7. 7
    user_service.sync app/services/user_service.py:7 plain call

    An ordinary function call you wrote by hand, with a Client already in your hand. No Depends, no FastAPI, no request. That is precisely why tests/unit/test_user_service.py can drive it with fake repositories and a NO_DB placeholder.

    returns → User, serialised through UserResponse
The mechanism

Why the parameters fill themselves

Two phases, and conflating them is the usual source of confusion.

At startup, once

The decorator registers sync_user. FastAPI inspects its signature and builds a plan: to call this, first produce a ClerkClaims from get_current_claims and a Client from get_supabase. It recurses, because get_current_claims has an annotated parameter of its own. The result is a dependency tree, computed once.

Per request

FastAPI walks that tree bottom-up, calling each function and caching the result per request — ask for both CurrentUser and CurrentClaims in one route and the token is still verified only once. Then it calls your function with the finished values as keyword arguments.

The order for one real request

Every dependency resolves before the body is entered, and response_model applies after it returns. POST /users/sync end to end:

before the body
1 get_current_claims → claims raises → 401, nothing below runs
2 get_supabase → db cached, so this is free after the first request
the body
3 sync_user(claims, db) → User both arguments already in hand
after the body
4 UserResponse → JSON narrows the result, clerk_id dropped here

Step 4 running after step 3 is what lets the function return the full internal User while clerk_id still never reaches the client. The route does not have to remember to strip it.

What decides where a parameter comes from

AnnotationFastAPI reads it as
Annotated[X, Depends(f)]call f and pass the result
a Pydantic modelthe JSON request body
str / int matching a {} in the paththe path
str / int not in the paththe query string

So claims and db arrive by dependency purely because CurrentClaims and SupabaseDep are Annotated[…, Depends(…)] aliases. Rename them to c and x and nothing changes. Strip the annotations and FastAPI decides they are query parameters and rejects the request as missing.

The aliases are the vocabulary, not the machinery. SettingsDep, SupabaseDep, CurrentUser and CurrentClaims in deps.py exist so a route can state what it needs in one word. CurrentUser is just the id string; CurrentClaims is the whole object. sync_user needs the latter because it writes email and full name into the row.
The unhappy paths

Every rejection exits the same door

Auth can fail in several distinct ways, and all of them produce one response shape from one handler. Nothing in the chain raises HTTPException.

No header at all

bearer_scheme returns None, and get_current_claims raises at deps.py:44.

Expired, forged, or wrong issuer

jwt.decode raises PyJWTError, caught and re-raised at security.py:47.

Claims present but wrong type

Pydantic raises ValidationError, caught and re-raised at security.py:53.

InvalidCredentialsError(DomainError)      # errors.py:43, status_code = 401
        ↓  escapes the dependency, never reaching the route
domain_error_handler                      # handlers.py:16
        ↓
{"detail": "invalid or expired token"}    # 401

The route body is never entered. tests/integration/test_current_user.py asserts exactly this, and it is the assertion that matters most in the file:

assert response.status_code == 401
assert reached == []   # the body never ran
Configuration

Where the trust actually lives

The entire chain reduces to two strings in .env, read through the cached get_settings() in core/config.py.

SettingRoleIf it is wrong
CLERK_PEM_PUBLIC_KEY verifies every signature every token is rejected, or worse, tokens from another issuer are accepted
CLERK_ISSUER pins which Clerk app is trusted a valid token from an unrelated Clerk instance passes

Because they are injected as a dependency rather than read from a module-level global, tests/conftest.py can replace the whole settings object in one line with app.dependency_overrides[get_settings] = fake_settings. In production that override map is empty and the real functions run on every request.

Checking it yourself

Prove the chain, cheapest first

# 1. the pure layer, no HTTP: self-signed tokens against the real verifier
uv run pytest tests/unit/test_security.py -v

# 2. the dependency, end to end on a throwaway app
uv run pytest tests/integration/test_current_user.py -v

# 3. the route is actually mounted
uv run python -c "from app.main import app; print([r.path for r in app.routes])"

# 4. a real rejection, no token supplied
uv run uvicorn app.main:app --reload
curl -i -X POST localhost:8000/api/v1/users/sync    # expect 401
  • Step 2 passing while step 4 returns 200 means a dependency is missing from the route.
  • A 422 instead of 401 means an annotation was dropped and FastAPI read the parameter as a query string.
  • {"detail":"Not authenticated"} rather than your own message means auto_error got left at its default.

Part two

The dependency vocabulary

app/api/deps.py is fifty-eight lines and imports from four other modules, yet it is the hinge the whole backend turns on. It is where a route stops describing how to obtain something and starts simply naming what it needs.

Orientation

What flows in, what comes out

Read this left to right. The left column is machinery that knows nothing about HTTP. The right column is code that cannot function without it. deps.py is the only thing that touches both.

Imports from

Why it sits in api/ and not beside the things it wraps. Depends is a FastAPI concept, and the architecture forbids FastAPI from appearing in core/ or db/. Putting SupabaseDep next to get_supabase would drag a web framework into the database layer. Keeping it here means db/client.py stays importable from a seed script with no web server in sight.
Anatomy

One line, two audiences

Every alias in the file has the same shape, and each half is read by a different reader.

SupabaseDep = Annotated[Client, Depends(get_supabase)]
                        ▲       ▲
                        │       └─ FastAPI reads this: "call get_supabase"
                        └───────── mypy reads this: "the value is a Client"

The two halves are independent, and nothing enforces that they agree. Write Annotated[str, Depends(get_supabase)] and mypy will happily let you call .upper() on a Supabase client, right up until it explodes at runtime. Keeping them honest is on you.

What mypy does with it

Treats the parameter as that type and nothing else. This is why sync_user can pass claims.email to a function expecting str and get checked properly.

What FastAPI does with it

Ignores the type entirely and looks only for a Depends marker in the metadata. Finds one, calls it, passes the result. Finds none, decides the parameter is a query string.

Reference

The four names, and when to reach for each

SettingsDep Configuration. Backed by @lru_cache, so it is built once per process. Reach for it when a route needs an environment value — a feature flag, the current environment name. Today only /health uses it.
SupabaseDep The database client. Also @lru_cached, deliberately: the client owns a connection pool, and one per request would exhaust connections and pay for a fresh TLS handshake every call. Every route that reaches a repository takes this.
CurrentClaims The full verified payload: clerk_id, email, full_name. Take this when you need more than identity — sync_user does, because it writes email and name into the row.
CurrentUser Just the Clerk id as a str. Take this for the common case: proving who is calling so you can filter or check ownership. A route that takes this cannot accidentally leak the caller's email into a response.

Choosing the narrower of the two is not a style preference. A route's signature is a claim about what it touches, and CurrentUser is the stronger claim.

Composition

Dependencies that depend on dependencies

The four names are not independent. Two of them are built out of a third, which is built out of a fourth, and FastAPI resolves the whole chain before your route sees anything.

bearer_scheme                 # deps.py:35  reads the Authorization header
    ↓
get_current_claims            # deps.py:39  None-check, then verify
    ↓                          #             ↳ core/security.py does the crypto
    ├── CurrentClaims         # deps.py:58  exposed directly
    ↓
get_current_user_id           # deps.py:48  discards everything but the id
    ↓
    └── CurrentUser           # deps.py:56

Because get_current_user_id is itself annotated with Depends(get_current_claims), the chain builds by the same mechanism a route uses. There is no special case for "nested" dependencies — it is annotations all the way down.

Each function runs at most once per request. A route taking both CurrentUser and CurrentClaims triggers get_current_claims once, not twice, so the RS256 signature is verified a single time. FastAPI caches by function within the request. This is separate from @lru_cache, which caches across requests for the whole process life.
Easily confused

Two caches, different jobs

 @lru_cacheFastAPI's per-request cache
livesprocess lifetimeone request

whythe object is expensive and immutablethe same value must not be recomputed mid-request

Putting @lru_cache on get_current_claims would be a critical security bug: the first user to sign in would have their identity served to everyone afterwards. The absence of that decorator is load-bearing.

The payoff

Why this shape earns its keep in tests

Going through Depends creates a seam. FastAPI checks an override map before calling any dependency, and that map is writable from a test.

app.dependency_overrides[get_settings] = fake_settings   # conftest.py:40

One line replaces configuration for the entire app. Compare it with get_supabase's internals, which are not injected — create_client is called directly, so tests/unit/test_db_client.py has to reach in and monkeypatch a module attribute instead:

monkeypatch.setattr(db_client, "create_client", fake_create_client)
monkeypatch.setattr(db_client, "get_settings", fake_settings)

Both work. The first is a supported seam; the second knows the internals of the module it patches and breaks if that module is refactored. That difference is the argument for dependency injection in one screen.

In production the override map is empty. Depends is not a testing device that happens to work at runtime — it is the runtime mechanism, and tests borrow it. Every request really does call get_settings() and get_supabase(); @lru_cache is what makes that free.
Failure modes

What it looks like when it is wired wrong

SymptomCause
422 with "field required" naming your parameter The annotation was dropped, so FastAPI read it as a query parameter.
{"detail":"Not authenticated"} instead of your own message auto_error left at its default, so HTTPBearer raised before your code ran.
A service receives a Depends object rather than a client An alias like SupabaseDep used in a service signature. Only the outermost function gets its arguments filled in.
A test's override is ignored The route depends on a different function than the one used as the override key. The key is the function object, not its name.
Two users see each other's data A per-request dependency was given @lru_cache.
Extending it

Adding a fifth name

Most sprints will not need one. The file should grow slowly — a new entry earns its place only when more than one route needs the same prepared value. The likely next candidate is a dependency that turns a clerk_id into the local users row, since almost every endpoint after this one needs users.id rather than the Clerk id.

  • Write the producing function. If it does I/O or holds business rules, it belongs in a lower layer and deps.py only wraps it.
  • Raise a DomainError subclass on failure, never HTTPException, so it exits through the one handler.
  • Bind the alias with Annotated[TheRealType, Depends(the_function)] and check the two halves agree.
  • Decide caching deliberately: @lru_cache only if the value is identical for every caller for the life of the process.
  • Name it for what it produces, not how — CurrentUser, not UserFromToken.

The mechanics of slotting that into a whole feature are on the adding a feature page.

Part three

Adding a feature, bottom-up

Eight steps, always in the same order, worked end to end on the feature that already exists: POST /users/sync. Follow the same sequence for rides, bookings, rewards and the pet shop and each one lands the same way.

The principle

Why the order is forced, not chosen

A layer may import only from the layers beneath it. That single rule determines the build order completely: you cannot write a thing before the thing it imports exists. Start at the top and you will write a route that calls a service that does not exist, discover the shape is wrong, and rewrite both.

6 · routeimports the service and the schemas
4 · serviceimports the repositories and the errors
3 · repositoryimports the schemas
2 · schemaimports nothing of yours but the enums
1 · migrationthe table the schema mirrors
write upward ↑   imports point downward ↓

Steps 5, 7 and 8 — the dependency, the wiring and the tests — fall outside that stack, and are covered in place below.

The method

Eight steps

  1. 1
    Write the migration supabase/migrations/ sql

    The schema is a deliverable checked into git, not something that lives only in the Supabase console. Decide the columns, the constraints and the enum types here, because every layer above is a mirror of this decision.

    CREATE TABLE users (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    clerk_id      TEXT UNIQUE NOT NULL,     -- the constraint the whole sync relies on
    email         TEXT NOT NULL,
    ...
    CONSTRAINT users_green_points_non_negative CHECK (green_points >= 0)
);

    The decision that mattered: clerk_id TEXT UNIQUE. That one constraint is what lets two concurrent first sign-ins race safely, because the database settles the conflict rather than Python. Push invariants into constraints wherever the database can hold them.

  2. 2
    Define the schemas app/schemas/ schemas

    Two models, split by direction. The domain model mirrors the table; the response model is what you are willing to put on the wire.

    class User(BaseModel):        # schemas/user.py:9  — internal, has clerk_id
class UserResponse(BaseModel): # schemas/user.py:23 — the wire, no clerk_id

    The decision that mattered: clerk_id appears in User and not in UserResponse. The token subject is an internal identifier; nothing outside the backend needs it. Splitting the models is what makes that omission structural rather than something you must remember in every handler.

    Shared literal types go in schemas/enums.py so Campus and UserRole are declared once and every model that uses them agrees with the SQL enum by construction.

  3. 3
    Write the repository app/repositories/ data

    One module per table. Every Supabase call in the codebase lives in one of these, and each function returns a domain model, never a raw dict. Functions take the client as their first argument rather than importing it, which is what keeps them callable from a script.

    def get_by_clerk_id(db: Client, clerk_id: str) -> User | None:
    res = db.table(TABLE).select("*").eq("clerk_id", clerk_id).limit(1).execute()
    return User.model_validate(res.data[0]) if res.data else None

    The decision that mattered: upsert(..., on_conflict="clerk_id", ignore_duplicates=True) instead of checking then inserting. A check-then-insert has a window between the two statements where a second request can slip in. Let the unique constraint decide.

    model_validate rather than User(**row), because supabase types res.data as a JSON union and ** requires a proven mapping.

  4. 4
    Write the service app/services/ logic

    All the branching lives here, and none of it knows what HTTP is. No Request, no HTTPException, no status codes — failures are DomainError subclasses.

    def sync(db: Client, *, clerk_id: str, email: str, full_name: str) -> User:
    existing = user_repository.get_by_clerk_id(db, clerk_id)
    if not existing:
        created = user_repository.create_if_absent(...)
        if not created:                            # another request won the race
            created = user_repository.get_by_clerk_id(db, clerk_id)
            if not created:
                raise DomainError("user sync failed")
        rewards_repository.create_if_absent(db, user_id=created.id)
        return created

    The decision that mattered: the re-read after a failed insert. ignore_duplicates returns nothing when another request inserted first, and that is a success, not an error — so read the row that the other request wrote. Race handling belongs here, where it can be tested without a database.

    Also here: creating the rewards row eagerly rather than on first visit to the pet page, so no later code has to cope with its absence.

  5. 5
    Add a dependency, only if needed app/api/deps.py api/

    Most features skip this step. Add a name only when more than one route will need the same prepared value. User sync needed nothing new — CurrentClaims and SupabaseDep already existed.

    See part two for the checklist when you do need one.

  6. 6
    Write the route app/api/routes/ api/

    The thinnest layer in the codebase. Declare what you need, call one service, return. If a route grows an if that is not about HTTP, it belongs in the service.

    router = APIRouter(prefix="/users", tags=["users"])

@router.post("/sync", response_model=UserResponse)
def sync_user(claims: CurrentClaims, db: SupabaseDep) -> User:
    return user_service.sync(
        db, clerk_id=claims.clerk_id, email=claims.email, full_name=claims.full_name
    )

    The decision that mattered: the annotation returns User while response_model is UserResponse. The function hands back the internal model and FastAPI narrows it on the way out, so clerk_id is dropped by the framework rather than by hand. tags groups the endpoint in /docs.

  7. 7
    Mount it app/api/router.py api/

    Two lines, and the easiest step to forget. Until this happens the route exists and is unreachable, and the tests that would catch it are the ones you have not written yet.

    from app.api.routes import users
api_router.include_router(users.router)

    The /api/v1 prefix is carried by api_router, so the final path is the concatenation of three pieces: /api/v1 + /users + /sync.

  8. 8
    Test the service, not the plumbing tests/unit/ tests

    The service holds the behaviour worth asserting, so test it directly with fake repositories and no database at all.

    monkeypatch.setattr(user_service, "user_repository", users)     # fakes
monkeypatch.setattr(user_service, "rewards_repository", rewards)

first = user_service.sync(NO_DB, **kwargs)
for _ in range(9):
    user_service.sync(NO_DB, **kwargs)
assert users.inserts == 1        # idempotent, the actual claim

    The decision that mattered: the test asserts idempotency by calling ten times, because "safe to call on every page load" is the whole contract of this endpoint. Test the promise, not the implementation.

    NO_DB is cast(Client, None) — the fakes never touch it, and the cast is what tells mypy you know.

Honest limits

What this method does not catch

Every layer above was verified without a database. That is the point, and it is also the gap: nothing in the suite proves the Pydantic models match the real columns.

Column drift

A field renamed in SQL but not in schemas/user.py passes every test and fails on the first real request.

Constraint violations

phone is NOT NULL and create_if_absent sends "". Legal, but it produces a user with no reachable number — which matters once bookings start revealing it.

So the last step of any feature is a real call against a real Supabase instance before you call it done.

Closing the loop

The verification ladder

Run these in order. Each one is slower than the last and only worth reaching when the one before it is clean.

# 1. style and imports, instant
uv run ruff check . && uv run ruff format --check .

# 2. types across app, tests and scripts
uv run mypy app tests scripts

# 3. behaviour, no database, no network
uv run pytest -q

# 4. the route is actually mounted
uv run python -c "from app.main import app; print([r.path for r in app.routes])"

# 5. auth really rejects
curl -i -X POST localhost:8000/api/v1/users/sync          # expect 401

# 6. the real thing, real token, real database
curl -i -X POST localhost:8000/api/v1/users/sync -H "Authorization: Bearer $TOKEN"
  • Migration written and checked into supabase/migrations/
  • Schemas split into domain and response, secrets absent from the response model
  • Every Supabase call inside a repository, returning models rather than dicts
  • Service raises DomainError subclasses only, never HTTPException
  • Route is thin, mounted on the router, and tagged
  • Service tested against fakes; the assertion states the promise, not the implementation
  • Steps 1 to 6 of the ladder green, and step 6 run once against real Supabase

Part four

Errors, and why they are ours

Four small classes and one handler. The payoff is that business logic never learns what an HTTP status code is, and every failure leaves the app through the same door.

The problem

What raising HTTPException would cost

The obvious approach is for a service to raise HTTPException(404) where the problem is found. It works, and it quietly welds two things together that should not be.

Business logic stops being reusable

A service that raises HTTPException can only be called from inside a web request. The seed script, a scheduled ride-completion job, a test — none of them have a request, and none should have to import FastAPI to call sync.

The status code decision scatters

"A missing ride is a 404" ends up written in six services. Change your mind and you change six files, and miss one.

So services raise errors that describe what went wrong in the domain, and exactly one module decides what that means over HTTP.

The design

One base class, status declared on the subclass

Every error carries the status it maps to as a class attribute. That is the trick that keeps the handler from growing an if chain.

class DomainError(Exception):     # errors.py:13
    status_code: int = 500          # the default when nothing more specific fits

    def __init__(self, detail: str) -> None:
        super().__init__(detail)
        self.detail = detail
DomainError500 — a business rule was violated and no subclass fits. Used directly in user_service.py when a row cannot be found or created after a race.
NotFoundError404 — the resource does not exist, or the caller may not know that it does.
PermissionDeniedError403 — authenticated, but not allowed to do this. A booking that is not yours.
InvalidCredentialsError401 — the token is missing, malformed, expired, or not signed by Clerk.

Note that NotFoundError deliberately covers "you may not know it exists". Returning 404 rather than 403 for someone else's booking hides whether that id is real, which is a security decision encoded in the choice of error class.

The path

How an error travels out

Nothing catches it in between. The raise unwinds the stack all the way to the app boundary.

raised
1verify_clerk_token raise InvalidCredentialsError, security.py:47
unwinds
2get_current_claims — does not catch it
3sync_user — never entered at all
caught
4domain_error_handler → JSON reads .status_code and .detail, handlers.py:16

Why one registration covers four classes

app.add_exception_handler(DomainError, domain_error_handler)   # handlers.py:39

Starlette walks the exception's inheritance chain looking for a match. An InvalidCredentialsError is not registered, but its parent DomainError is, so the handler runs. Adding a fifth error type in sprint 3 is one class in errors.py and no change to handlers.py.

Easily missed

Three error paths, not one

Only one of these is yours. Knowing which is which saves a lot of confused debugging, because the response shapes differ.

ValueError in a Pydantic validator, or a bad request body FastAPI's built-in validation handler 422 {"detail": [{"loc":…, "msg":…}]}
anything else (KeyError, TypeError) nobody 500 Internal Server Error

Your normalize_phone validator in schemas/user.py raises ValueError, so it takes the middle row: a 422 with a list of field errors, not your {"detail": "..."} shape. That is correct — field-level problems belong to the request, not the domain — but the frontend has to handle both shapes.

The third row is the one to watch. An unhandled exception returns the string Internal Server Error, not JSON. tests/unit/test_exceptions.py asserts the difference: a bare DomainError produces {"detail": "something went wrong"}, which only happens because a handler is registered. A crash would not.
Tracking

What is recorded today: nothing

Worth stating plainly rather than implying otherwise. There is no logging call anywhere in app/. A 401 from a forged token and a 500 from a failed sync both vanish silently once the response is sent.

What the design does give you is the place to fix that. Every domain failure passes through domain_error_handler, so instrumentation is one function rather than an audit of every service:

add in the handlerbuys you
log at WARNING for 4xx, ERROR for 5xxSplit "the caller did something wrong" from "we are broken". Only the second should page anyone.
log request.method and request.url.pathThe handler already receives request and currently ignores it. Which endpoint failed is the first question you will ask.
exc_info=True on 5xxKeeps the traceback, including the from exc cause chain.
a request id, echoed in the bodyA user reports "it said error"; you find the exact request.

The cause chain is already preserved

raise InvalidCredentialsError("invalid or expired token") from exc   # security.py:47

The from exc matters. It attaches the original PyJWTError as __cause__, so a traceback shows both the domain error and the real reason underneath — expired signature, wrong issuer, malformed token. The client still gets one deliberately vague message; the traceback keeps the truth. That asymmetry is the point: detail for you, not for an attacker probing which half of the token is wrong.

The payoff

What this buys

1Services run anywhere. user_service.sync is callable from a script, a cron job, or a test with no FastAPI import. That is what tests/unit/test_user_service.py relies on.
2One place decides the wire format. Change the body from {"detail":…} to {"error":…} and every endpoint changes together.
3New error types are free. One class, no handler edit. RideFullError and InsufficientPointsError will slot in without touching anything else.
4One instrumentation point. Logging, metrics or Sentry go in the handler, not in fifty raise sites.
5Consistent errors for the frontend. Every domain failure has the same shape, so the client has one error path instead of one per endpoint.
Extending it

Adding an error type

  • Subclass DomainError in errors.py and set status_code.
  • Give it a docstring saying when it applies, in the voice of the domain rather than of HTTP.
  • Raise it from the service, never from a repository, and never from a route.
  • Do not touch handlers.py. If you feel you need to, the status probably belongs on the class instead.
  • Choose the class for what it reveals: NotFoundError over PermissionDeniedError when confirming existence would leak something.
