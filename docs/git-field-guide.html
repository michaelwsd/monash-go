Part one

What a commit actually is

Every confusing thing git does becomes obvious once three objects are clear: a commit, a branch, and HEAD. Rebase, reset and merge are all just these three moving.

The three objects

Snapshot, label, pointer

a commit A full snapshot of the tree, plus a pointer to its parent, plus author and message. Its hash is computed from all of that. Change any part and it is a different commit with a different hash. Commits are never edited, only replaced.
a branch A movable label pointing at one commit. That is the whole implementation — a file containing a hash. This is why branching is instant and why deleting a branch deletes no commits.
HEAD A pointer to the branch you are on. HEAD~1 means "one commit back from here", HEAD~3 means three back.
three commits on one branchon main

A branch is a label on the newest commit; HEAD says which label you are standing on. HEAD~1 counts backwards from there.

Arrows point backwards. Each commit knows its parent; no commit knows its children. That single fact explains why git can rewrite recent history cheaply but has to rebuild everything after the point you touch.
The core idea

Rebase replays, it does not move

The word "rebase" suggests picking your commits up and setting them down elsewhere. That is not what happens. Git takes the changes your commits introduced, applies them one at a time on top of the new base, and creates brand new commits with new hashes. The originals are abandoned, not relocated.

before — you branched, then main moved onon feature

Two lines of work sharing a common ancestor. This is the situation rebase and merge both exist to resolve.

after git rebase main — f1 and f2 are gone, f1′ and f2′ are newon feature

Same changes, different parents, therefore different hashes. The originals are abandoned rather than moved.

The result is a straight line: it now looks as though you started your work after everything on main, rather than alongside it. Same changes, different parents, different hashes.

The choice

Rebase or merge

Both integrate main into your branch. They differ in what the history looks like afterwards and in whether existing commits survive.

git rebase main

Linear history, no merge commit. Your commits are rewritten with new hashes. Best for a branch only you have, before opening a PR.

git merge main

Adds one merge commit joining the two lines. Nothing is rewritten, every hash survives. Best when others have your branch, or when you want the branch point preserved.

git merge main — one new commit joins the two lineson feature

Nothing is rewritten. Every original hash survives and the branch point stays visible in the history.

git rebase main — replayed on the tip, new hasheson feature

Linear. f1 and f2 no longer exist: f1′ and f2′ are new commits carrying the same changes.

The golden rule. Never rebase commits that other people have already pulled. Rebasing replaces them, so everyone else still has the originals and git will try to reconcile two versions of the same work. On your own feature branch, rebase freely.
Doing it

The everyday rebase

git fetch origin

Updates your origin/* refs. Changes nothing in your working tree, so it is always safe.

git fetch origin — only your origin/* pointers moveon my-feature

Your branch and your files do not move at all. Only the origin/* pointers catch up, which is why fetch is always safe to run.

git rebase origin/main

Replays your branch's commits on top of the latest main, one at a time, oldest first.

git rebase origin/main — afteron my-feature

Your commits are rebuilt one at a time, oldest first, on top of the fetched main.

If a replay hits a conflict, git stops mid-rebase and hands you the working tree to fix. You have three ways out, and they matter:

commandwhat it does
git rebase --continueYou fixed the conflict and ran git add. Carry on with the next commit.
git rebase --skipDrop the commit being replayed entirely. Correct when its change is already present upstream.
git rebase --abortGive up and put everything back exactly as it was. Nothing is lost.
a conflict stops the replay part-wayon my-feature

--continue after fixing and staging · --skip drops f2 entirely · --abort restores everything from before the rebase.

--abort is the one to remember. Any time a rebase turns confusing, aborting returns you to the state before you started, and you can try a merge instead.

Pulling with rebase

git pull --rebase

Fetch, then replay your local commits on top of what you fetched, instead of creating a merge commit. This is what keeps a shared branch's history from filling with "Merge branch main into main" noise.

git pull --rebase — fetch, then replay yours on topon sprint2

No merge commit. Your local commits are rebuilt on top of what you fetched, which keeps a shared branch free of "Merge branch sprint2" noise.

When you and main have both moved

The most common git wall on a shared branch. You committed on main, someone else pushed to main first, and now your push bounces. Two different messages describe the same situation:

what git sayswhat it means
! [rejected] main -> main (non-fast-forward) Updates were rejected because the tip of your current branch is behindOn push. The wording is misleading: you are usually diverged, not simply behind. Both of you added commits.
hint: You have divergent branches and need hint: to specify how to reconcile them.On pull, when git has no configured preference for merging or rebasing.
why the push was rejectedon main

You both started from base. A normal push can only fast-forward, meaning add commits on the end of what is already there. Your main is not on the end of theirs, so git refuses rather than throwing their work away.

Confirm it is a divergence rather than a simple "behind" before you decide anything:

git fetch origin && git status -sb

Prints something like ## main...origin/main [ahead 1, behind 2]. Both numbers non-zero means diverged. Only behind means a plain git pull is all you need.

git pull --rebase

Takes their two commits as the new base and replays yours on top. Your commit gets a new hash; theirs are untouched.

after git pull --rebase — one line againon main

Your commit was replayed on top of theirs and now has a new hash. The branch fast-forwards cleanly, so git push works with no force and nobody loses anything.

git push origin main

Now a fast-forward, so it just works. No force, no flags.

Do not force-push here. This looks like the force-with-lease case from part two, and it is the opposite. There you were rewriting your own feature branch. Here main is shared, and forcing would delete your teammate's two commits from the remote. If a push to a shared branch is rejected, the answer is always to integrate their work, never to overwrite it.
git config --global pull.rebase true

Set once. Makes git pull rebase by default, so the "divergent branches" hint stops appearing and you stop accumulating merge commits on shared branches.

If the replay hits a conflict, it is the ordinary rebase conflict from earlier in this page: fix the file, git add it, then git rebase --continue. git rebase --abort puts you back to the rejected-push state with nothing lost.

Interactive rebase: tidying before a PR

git rebase -i HEAD~4

Opens an editor listing your last four commits, oldest at the top. Change the word at the start of a line to change what happens to that commit, save, and close.

squash / fixup — three commits become oneon my-feature

squash keeps every change and lets you combine the messages. fixup is identical except it throws the folded-in messages away, which is what you want for "fix typo" commits.

There is no git squash command. This is the whole mechanism: git opens a file listing your commits, and you edit the word at the start of each line. Save and close, and git carries out what you wrote.

1. What git opens

pick a1b2c3 add ride schema
pick d4e5f6 fix typo
pick 7g8h9i wip
pick 01890bb address review

Oldest at the top, which is the opposite of git log. Every line starts as pick.

2. What you change it to

pick   a1b2c3 add ride schema
fixup  d4e5f6 fix typo
fixup  7g8h9i wip
reword 01890bb address review

Two commits folded into the first, and the last one kept with a better message. Four commits become two.

squash or fixup? Both fold the commit upward. squash opens an editor so you can combine the messages; fixup silently discards the folded-in message. For "fix typo" and "wip" commits you almost always want fixup, because their messages are worth nothing in the final history.
keywordeffect
pickKeep it as is. The default for every line.
rewordKeep the changes, edit the message.
squashFold into the commit above, and combine both messages.
fixupFold into the commit above and discard this message. What you want for "fix typo" commits.
dropDelete the commit and its changes.
drop — and why the commits after it change hash tooon my-feature

You only edited c, yet d became d′. Every commit after the one you touched is rebuilt, because a commit’s hash includes its parent.

Deleting a line does the same as drop. Reordering lines reorders the commits. Since every commit after the first change gets rebuilt, this is rewriting history, so the golden rule applies.

Part two

Undoing things

Most git panic comes from not knowing which of the three resets you want. They differ in exactly one way: how much they throw away.

The three trees

Where your changes live

Every undo command is described in terms of these three. Learn them once and reset stops being frightening.

working tree The files on disk, as your editor sees them.
index (staging area) What you have run git add on. The draft of your next commit.
HEAD The last commit. What git add is measured against.
Reset

Soft, mixed, hard

All three move the branch pointer to the commit you name. They differ only in whether they also wipe the index and the working tree.

 moves HEADclears indexdeletes your editsuse when
--softyesnono Wrong message, forgot a file, not ready to commit yet.
--mixed (default)yesyesno You want to re-choose what goes in the commit.
--hardyesyesyes You genuinely want the work gone. Nothing warns you.

Undoing the last commit, keeping the work

git reset --soft HEAD~1

The commit stops existing. Every file it contained is still staged, exactly as it was a moment before you committed. Run git commit again with a better message, or stage more first.

git reset --soft HEAD~1on my-feature

The commit is gone but everything it contained is still staged, exactly as it was a moment before you committed.

Two neighbours worth knowing, because they are shorter for the common case:

commandwhen
git commit --amendFix the last commit's message or add a forgotten file, in one step. Same rewrite, less typing.
git reset HEAD~1Mixed. Commit gone, changes kept but unstaged, so you can re-select what belongs.
git restore --staged <file>Unstage one file without touching commits at all.
git reset --mixed HEAD~1on my-feature

Same pointer move, but the index is cleared too: your changes are still in your files, just unstaged.

git commit --amend — replaces, never editson my-feature

A one-commit rebase. The old commit is abandoned and a new one takes its place, so the hash changes and the golden rule applies.

git reset --hard HEAD~1on my-feature

Pointer, index and your files. The edits are deleted. Recoverable through the reflog only because the work had been committed once.

Reset rewrites history; revert does not. If the commit has already been pushed and others may have it, use git revert <hash>. That creates a new commit undoing the old one, so nobody's history changes underneath them.
git revert — safe on pushed commitson main

The bad commit stays in history. A new commit undoes its changes, so nobody else’s history is rewritten underneath them.

The safety net

reflog: nothing is really gone

Git records every position HEAD has held, including the ones a rebase or reset abandoned. Commits stay recoverable for about 90 days even when no branch points at them.

git reflog

Lists recent HEAD positions, newest first, each with a name you can use like a hash.

outputmeaning
50b793a HEAD@{0}: reset: moving to HEAD~1Where you are now, and how you got here.
1b81d8d HEAD@{1}: commit: add POST /users/syncThe commit that reset abandoned. Still fully intact.
git reset --hard HEAD@{1}

Puts everything back to before the mistake. This is why --hard is survivable in practice: the reflog remembers, as long as the work was committed at least once.

reflog recovery — putting an abandoned commit backon my-feature

The abandoned commit was never deleted, only left with nothing pointing at it. Git keeps it for about 90 days.

Before anything risky, make a free backup. git branch backup-x pins your current commits under a second name. It costs nothing, and it means you do not have to trust yourself to read reflog correctly while stressed.
Pushing rewritten history

force-with-lease, never force

Rebasing or resetting a branch you have already pushed means the remote and your local copy disagree, and a normal push is refused.

git push --force-with-lease origin my-branch

Overwrites the remote branch, but only if it still points where your last fetch saw it. If a teammate pushed in the meantime, the push is rejected instead of destroying their commit.

pushing rewritten historyon my-branch

--force-with-lease replaces the remote line, but only if it still points where your last fetch saw it. Plain --force skips that check.

do--force-with-lease, after a git fetch so the check is meaningful.
avoid--force. It skips the check and will silently erase work you never saw.
neverForce-push a shared branch without telling the people on it first.

Part three

Inspecting, and reading what you get back

Most git commands answer a question. The trick is knowing which question each one answers, and how to read the answer without guessing.

Where am I

status, and what its columns mean

git status --short

Two columns per line. Left column is the index, right column is the working tree. This is the part people misread.

linemeaning
M app/main.pyModified and staged. M is in the left column. This goes in your next commit.
M app/main.pyModified, not staged. Note the leading space. This will not be committed.
MM app/main.pyStaged, then modified again. The commit gets the earlier version.
A app/schemas/user.pyNew file, staged.
?? app/services/ride.pyUntracked. Git has never seen it and will not commit it.
R src/app/main.py -> app/main.pyDetected as a rename, not a delete plus an add, so history follows the file.
What happened

log, shaped to the question

commandanswers
git log --oneline -10What are the last ten commits?
git log --oneline --graph --allHow do my branches actually relate? The one to run when confused.
git log --stat -3Which files did the recent commits touch, and how much?
git log -p app/api/deps.pyEvery change ever made to this file, with diffs.
git log --follow app/main.pySame, but keep going across renames.
git log -S "verify_clerk_token"Which commit introduced or removed this string? The best bug-archaeology tool git has.
git log main..my-branchWhat is on my branch that is not on main? Exactly the PR contents.
git log --author=michaelwsd --since="2 weeks"Scoped by person and time.
two dots versus threeon my-branch

main..my-branch = f1 f2 · my-branch..main = m1 m2 · main...my-branch = all four.

Two dots versus three. a..b means "on b but not a", a one-directional question. a...b means "on either but not both", which is what you want when two branches have diverged and you need to see it.
One commit

show, and reading a diff header

git show 50b793a

Message, metadata and the full diff for one commit. Add --stat for just the file list.

diff linemeaning
diff --git a/x.py b/x.pya/ is the before, b/ is the after. Always this pair.
similarity index 67%Git decided this is a renamed file, 67% unchanged.
@@ -37,7 +52,7 @@This hunk was 7 lines starting at line 37 before, and is 7 lines starting at line 52 after.
- old lineRemoved.
+ new lineAdded. A changed line shows as one of each.
Comparing

diff answers a different question depending on the flags

commandcompares
git diffWorking tree against the index. What you have changed but not staged.
git diff --stagedIndex against HEAD. Exactly what your next commit will contain. Run this before every commit.
git diff HEADWorking tree against the last commit. Everything uncommitted, staged or not.
git diff main...my-branchWhat your branch adds, ignoring anything main gained since you branched. What a reviewer sees.
Divergence

Answering "why was my push rejected"

When git says your branch is behind, it is often wrong in a useful way: you have usually diverged, which is a different problem with a different fix. Two commands settle it.

git fetch origin && git rev-list --left-right --count origin/main...main

Prints two numbers: how many commits exist only on the remote, and how many only locally.

diverged: commits on each side that the other lackson main

rev-list --left-right --count prints 2    3 here: two only on the remote, three only local. Not "behind" — diverged.

outputsituation
0 3You are ahead by 3. A normal push works.
2 0You are behind by 2. git pull is the right advice.
2 7Diverged. Pulling will merge or replay; rebasing or force-with-lease may be what you actually want.

Same work, different hashes

After a rebase or an amend, the remote holds old copies of commits you still have locally under new hashes. They look like different commits but contain identical changes. patch-id proves it, by hashing the diff instead of the commit:

git show <hash> | git patch-id --stable

Two commits with the same patch-id introduce exactly the same change. If every remote-only commit matches a local one, force-pushing loses no work.

same work, different hashes — proved by patch-idon main

Different hashes, identical patch-id. The pairs introduce exactly the same change, so force-pushing yours loses nothing.

Blame

Who wrote this line, and why

commandanswers
git blame app/core/security.pyWhich commit last touched each line.
git blame -L 35,55 app/api/deps.pySame, limited to a line range. Usually what you want.
git show <hash-from-blame>The step that matters. Blame gives you a hash; the commit message gives you the reason.

This is the payoff for writing commit messages that explain the decision rather than restate the diff. Blame plus a good message answers "why is this like this" in two commands.

Part four

Everyday commands and recipes

The commands worth having in your fingers, and the handful of situations that come up often enough to be worth a recipe.

Daily

The loop

commandwhat for
git switch -c my-featureCreate and move to a new branch. Modern replacement for checkout -b.
git switch mainMove between existing branches.
git add -pStage hunk by hunk, answering y/n. The easiest way to keep commits focused.
git commitOpens your editor, so you can write a body. -m encourages one-liners.
git push -u origin my-featureFirst push of a branch. -u links it so later pushes need no arguments.
Recipes

Situations that keep happening

I committed to main by mistake

git branch my-feature

Pin the commits under a real branch name first, while main still points at them.

rescuing commits made on main by mistakeon main

Branch first, then reset main. The commits survive under the new name, so the --hard that follows costs nothing.

git reset --hard origin/main

Put main back where the remote has it. Safe here only because the previous line saved your work.

git switch my-feature

Carry on where you left off, now on the right branch.

I need to switch branches but am not ready to commit

git stash push -m "half-done ride search"

Shelves your changes and gives you a clean tree. Name it, or in two days you will have four anonymous stashes.

git stash — work shelved off to the sideon my-feature

The stash is not a commit on your branch. It sits to one side until you pop or apply it.

git stash list && git stash pop

pop applies the newest and deletes it; apply keeps it in the list.

I want one commit from another branch

git cherry-pick <hash>

Replays that one commit onto your current branch as a new commit. Useful for lifting a bug fix out of a long-running branch.

git cherry-pick — replay one commit hereon my-feature

One commit copied across as a new commit with a new hash. The original stays where it was.

I want to throw away my uncommitted changes to one file

git restore app/api/deps.py

Working-tree version back to HEAD. There is no undo for this, because the content was never committed. Check git diff first.

Someone force-pushed and my branch looks wrong

git fetch origin && git reset --hard origin/my-branch

Adopt the remote version wholesale. Run git log first to check you have nothing local worth keeping, and git branch backup if unsure.

Habits

Five that prevent most trouble

1git status and git diff --staged before every commit. Two seconds, catches the wrong file every time.
2git fetch before deciding anything about the remote. Opinions formed on stale refs are wrong.
3git branch backup-x before any rebase, reset or force-push. Free, and it removes the fear.
4Commit early and often locally. Uncommitted work is the only work git cannot recover.
5Write the message for whoever reads it in six weeks. The diff says what changed; the message should say why.
If it goes wrong

The recovery order

stepwhy
1. stop, do not run more commandsMost lost work is lost by the third panicked command, not the first mistake.
2. git statusEstablish where you actually are, including whether a rebase or merge is mid-flight.
3. git reflogFind the commit you want to be at. It is almost always still listed.
4. git branch rescue <hash>Pin it before moving anything, so a wrong next step costs nothing.
5. git reset --hard <hash>Only now, and only once you have the rescue branch.

The single exception the reflog cannot save you from is work that was never committed. That is the real argument for habit 4.

Part five

Forks, remotes and pull requests

Everything so far happened on one machine. This is what changes once a second copy of the repository exists on a server, and a third exists in someone else's account.

The concept

A remote is a saved URL

That is the entire idea. A remote is a nickname for a repository somewhere else, so you can type origin instead of the full address every time.

a remote is a saved URL with a nickname

Nothing about the name origin is special. It is the default nickname git clone writes for wherever you cloned from. You can add more, rename them, or delete them.

git remote -v

Lists every remote you have, with its URL and whether it is used for fetching, pushing, or both.

outputmeaning
origin git@github.com:you/repo.git (fetch)Where git fetch with no arguments reads from.
origin git@github.com:you/repo.git (push)Where git push writes to. Usually the same URL, but it need not be.
origin is not a keyword. It is just the nickname git clone happens to write for wherever you cloned from. You can rename it, delete it, or have five remotes with any names you like. Git treats them all identically.

The two names you will meet

origin By convention, the copy you can push to. On this project that is michaelwsd/monash-go itself. On a fork it is your fork.
upstream By convention, the original project you forked from and cannot write to. You fetch from it to stay current, and you never push to it.
Which flow are you in

Fork, or branch on the same repo

Two different workflows, and picking the wrong one is where most of the confusion starts.

Branch on the same repo

You have write access. One remote, origin. Branch, push, open a PR from your branch to main. This is what MonashGO uses — PRs #3 and #4 came from error_handler and sprint2 on the same repository.

Fork

You do not have write access, so you take your own server-side copy first. Two remotes, origin and upstream. Standard for contributing to open source or to another team's project.

Everything below covers the fork flow, since it is the one with parts that are not obvious. The same-repo flow is the same minus upstream and minus the fork step.

Setup, once

Three copies, two remotes

three copies, two remoteson your fork

upstream is the original you cannot write to; you only ever read from it. origin is your fork, which you own and push to. Both names are conventions, not git features.

Forking is a GitHub action, not a git command: press the button and GitHub makes you a server-side copy. Then clone your fork, not the original.

git clone git@github.com:you/monash-go.git

Creates the local copy and sets origin to your fork automatically.

git remote add upstream git@github.com:michaelwsd/monash-go.git

Adds a second remote pointing at the original. Now you can read their changes without giving up your own push target.

git remote -v

Confirm you have exactly two: origin to your fork, upstream to theirs.

The loop

Making a change and opening a PR

git fetch upstream && git switch -c my-feature upstream/main

Branch from their latest main, not from whatever your fork happens to hold. This one habit prevents most fork-sync pain.

git add -p && git commit

Work as normal. Small, focused commits with real messages: a reviewer reads them one at a time.

git push -u origin my-feature

Pushes to your fork. -u links the branch so later pushes need no arguments. This never touches the original project.

opening a pull requeston my-feature

The PR itself happens on GitHub, not in git. It asks the maintainers to pull your branch into their main. Push more commits to the same branch and the PR updates automatically.

GitHub then shows a "Compare & pull request" button. The PR names two things: the branch you are offering, and the branch you want it merged into. Everything after this is conversation.

during reviewwhat to do
reviewer asks for a changeCommit and git push. The PR updates itself; you never open a second one.
your branch has messy commitsgit rebase -i, then git push --force-with-lease. Safe: the branch is yours.
main moved and the PR conflictsRebase onto the new upstream/main. Covered below.
PR is mergedDelete the branch on both sides. Its commits now live in main.
Staying current

Your fork does not update itself

A fork is a snapshot taken the moment you pressed the button. It learns nothing about the original afterwards unless you tell it to.

your fork has gone staleon my-feature

Your fork does not update itself. While you worked, upstream/main gained commits your branch has never seen.

git fetch upstream

Reads their latest into upstream/main. Changes nothing of yours.

git rebase upstream/main

Replays your commits on top of theirs, so your PR applies cleanly and reviewers see only your changes.

after rebasing onto upstream/mainon my-feature

Your two commits are replayed on top of the latest upstream. New hashes, so the push back to your fork needs --force-with-lease. That is safe here: the branch is yours alone.

git push --force-with-lease

Your commits have new hashes, so the branch on your fork must be replaced. The PR picks it up automatically.

This is the one place force-pushing is routine. The rule from part two still holds: never force a shared branch. A PR branch in your own fork is not shared — you are its only author, and rebasing it is normal practice while a PR is open.

Updating your fork's main

git fetch upstream && git merge --ff-only upstream/main

--ff-only refuses if your main has drifted, which is exactly what you want. Your fork's main should be a mirror, never somewhere you commit.

git push origin main

Optional. Only needed to make the fork look current on GitHub; your work does not depend on it.

Reference

Remote commands worth knowing

commandwhat for
git remote -vList remotes and their URLs.

git remote set-url origin <url>Repoint one, e.g. switching HTTPS to SSH.

Remote-tracking branches are read-only caches. origin/main is your record of where main was on the remote at your last fetch. It only moves when you fetch or push, never on its own, which is why an opinion formed without fetching first is usually out of date.
